# Production workflow (portable)

Read alongside [style-contract.md](style-contract.md). This is a result-first demo recipe, not a claim that every source was generated by the app being taught. Current explicit choices and protected project instructions take precedence.

## 1. Build a source-backed beat map

Start from the final result and ask what the viewer will learn to reproduce. Inventory source duration, dimensions/fps, audio, capture quality and source hashes. Compare supplied takes for clarity, natural pace and completed sentences; prefer the user's stated take unless another has a concrete advantage. Reuse cached verbatim word timings for an unchanged source. Keep the narration as the timeline clock.

The beat map records output frames, exact spoken words/source times, actual UI action/evidence, hook/title/caption, presenter source offset and engine. Use integer, half-open frame ranges [start,end). Picture ranges cover the whole output with no unintended gap or overlap. Overlay windows may overlap picture by design.

For NEW narration, refine the user's wording rather than making it sound like an ad agency. A useful speakable shape is:

- Curiosity: a short promise tied to the visible result, not “AI is changing everything.”
- Bridge: “Want to know how I made it?”
- Pain/tool: one sentence about the actual workflow friction and the feature that helps.
- Steps: “I added [source], then [reference]. This prompt keeps [constant] and changes [target].” Match demonstrated capability; do not promise arbitrary perfect replacement.
- Takeaway: what the viewer can reuse.
- CTA: save + requested keyword + the resource actually prepared.

Do not force identical words, a tool's branding, an offer, or a fixed 50 seconds onto another topic. If recording is requested, give the speakable script first. A duration target may require fewer words, not faster unintelligible playback or truncating the last sentence.

## 2. Capture meaningful actions, not waiting

Use the requested signed-in browser and supported controls. Record feature selection, new workspace, source/reference additions, prompt/connection and applicable skill selection. Before a long take, confirm changing frames and real cursor movement. Capture each action's before-state, click and after-state. Do not fabricate upload success, OS file-picker coverage or generation completion.

Retain raw capture, source-time metadata and pointer events. Store capture pixel dimensions, pointer coordinate-system dimensions and any crop offset. If the native cursor is already visible, do not overlay a second one. Keep clicks at their observed source time. Screen sampling is not necessarily encoded fps; disclose actual sampling in the project receipt.

If continuous capture fails, timestamped changing frames may be used only with honest provenance and adequate motion for the requested tutorial. If the user requires a genuine continuous screen recording, do not silently downgrade to that fallback; repair the capture or report the missing segment.

Readability starting targets for new work (adjust to content): orient on the active control for about 0.4-0.7s, show the real click/result for at least 0.4s, then hold the meaningful state 0.8-1.5s. Let an important prompt/example settle about 1.5-2.5s. These are pacing aids, not permission to stretch an approved edit. If the whole prompt cannot be read, highlight the key clause and supply the complete prompt as the promised resource; do not claim the whole prompt is readable.

## 3. Make a vertical camera over real footage

Fill the frame with the actual capture, crop to one control or proof at a time, and retain enough UI context to orient the viewer. Pan/zoom toward the narrated target and land before its payoff word. Hold the result; never sweep past every detail. Do not remake the website as a decorative mockup.

Normalize pointer and camera coordinates once. For source-pixel coordinates, `sourceX = (pointerX - cropOffsetX) * sourceWidth / pointerWidth` and likewise y, only if the recorded crop/coordinate relationship matches that mapping. If a capture crops a larger viewport, use its actual full-scale ratio before subtracting crop pixels. Document the mapping and verify a corner/control against the real capture. Do not inherit Canvas's 1.1 ratio.

Use source-time `sourceStart + localFrame / outputFps * playbackRate` for both video and cursor events. Camera position is output-time driven. Avoid a cursor that arrives after the UI already changes. Scale the capture, not cursor glyph size, so the cursor remains readable. Preserve existing camera/pointer tracks during a surgical presenter revision.

## 4. Lock audio and build optional presenter

Keep one audio owner. Preserve accepted audio packets when changing only picture. For a new mix, cut between complete words with roughly 30-200ms contextual padding; avoid duplicate speech, missing breaths and clicks. Use short fades only where audio edits are actually made. Match timbre/pace/level of an authorized synthetic pickup and listen across both joins. No arbitrary music or additional voice generation to “polish” an accepted edit.

When a NEW presenter is approved, select the existing authorized look/engine, verify support and pricing, pack word-safe passages into one generation where practical, and record the exact mapping. Usually three roughly five-second appearances connect the introduction, key explanation and CTA; adapt to real sentence boundaries. Do not cut exactly five seconds through a word. Do not reuse old speech to fake new lip sync.

Decode and inspect actual transparency, hair/hands and natural proportions. Prepare output-fps frames without treating a 25fps source as a 30fps sequence. Crop only confirmed transparent padding across the full motion range; preserve gesture extent. See implementation.md for the alpha workflow. Never upscale previously reduced frames if a higher-resolution native source is available.

The large corner presenter remains flush bottom-left. A useful appearance has mouth/gesture motion, no frozen tail, no opacity plate and no floating entrance. Caption location depends on the WHOLE overlapping caption page. Validate alpha at the text rows; the bounding rectangle can contain transparent space where text safely fits, but never assume the v6 clearance works with another pose.

## 5. Close, verify, deliver

Preserve the full spoken save/comment/resource sentence. Show the CTA with a readable hold, then a short deliberate settled ending (roughly 0.5-1s where the source permits). Do not repeat the result or freeze the presenter for lack of footage. A held background in an intentional final tail is different from a frozen speaking avatar.

Map brand requirements to actual frames and sources. Offers need current validity, term/eligibility/renewal and arithmetic checks, not inherited historical copy. Have the actual promised resource ready before release. The CTA itself never authorizes an account-wide DM trigger.

Run the staged gates in SKILL.md and record failures as failures. View rendered output, not only source components. Test phone readability, meaningful motion, first/last speech, each cut and affected caption/presenter window. No numerical “quality score” substitutes for inspection. Preserve sources and intermediate references. Three creative passes maximum; if a required gate remains blocked, deliver the completed reviewable parts with exact limitations rather than claiming full completion.

Use the existing task review service if practical, after identifying its process/root; do not kill unrelated servers or multiply ports. Confirm the current master URL, playback to end, decoded dimensions and actual display-drop count. Keep subjective listening and lip-sync observations separate from counters. Report local completion, acceptance and external release as distinct states.
